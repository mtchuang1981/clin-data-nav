# v0.8.0 Public Evidence Ledger Pilot Design

Status: approved design

Date: 2026-09-19

## Purpose

Evaluate whether the immutable `clin-nav` v0.8.0 evidence-ledger workflow can
record source review, claim support, citation location, version status, and
review needs for a small set of public evidence questions. This is an evidence
process audit, not a model-response benchmark, a human-effectiveness study, or
a scientific-validity assessment.

The pilot uses four frozen public cases: CDISC, OMOP, RWE/TTE, and SAS/Lex
Jansen. It reuses the packaged offline checker and the repository checker. It
does not modify the v0.8.0 schema during execution.

## Decisions

- Use a controlled manual audit rather than automated HTTP or metadata
  extraction.
- Use one case per evidence domain and three fixed material claims per case.
- Interpret freshness by source type and version state, not by a universal
  document-age threshold.
- Use a 90-day project review interval for every reviewed source in this pilot.
  `review_due_on` is a review-policy date, not an expiration claim.
- Keep complete ledgers, audit records, review notes, source copies, and raw
  checker output outside the repository.
- Permit only an aggregate verification record and external-file hashes in
  Git.
- Do not run model A/B tests, repeated generations, or a 72-cell campaign.
- Do not start v0.9.0 development in this pilot.

## Freshness Semantics

The pilot separates four concepts:

1. `version_status`: `current`, `superseded`, `in-development`, or `unknown`;
2. `checked_on`: the date on which the actual source and its status were
   inspected;
3. `newer_source_search`: the official entry points searched and the result;
4. `review_due_on`: `checked_on + 90 days`, used only as a project review date.

Versioned standards and software documentation are compared with an official
current-version or release entry point. Methodology papers are not declared
stale merely because they are old; their audit instead records the search
cutoff, whether newer guidance was found, and the scope for which the paper is
still being used. Implementation papers are never promoted above the
authority of the governing standard or official product documentation.

The v0.8.0 ledger is a closed schema and has no first-class
`version_status`, `checked_on`, or `newer_source_search` fields. Adding those
keys would correctly fail validation. The pilot therefore records them in a
companion source-audit file linked by `source_id`. Whether the required meaning
is clear in the ledger itself is an evaluated outcome, not an assumption.

## Frozen Case Catalog

Every case has exactly three required claims. Completeness is assessed against
these twelve claims only; the pilot does not claim domain-wide completeness.

### Case 1: `cdisc-version-status`

Required claims:

1. The reviewed ADaM implementation-guide page associates ADaMIG v1.3 with
   the ADaM v2.1 model.
2. The reviewed CDISC development-status page labels ADaM and IG v3.0 as in
   development at the pilot cutoff.
3. An in-development or public-review artifact must not be described as a
   current final standard solely because its page is publicly accessible.

Required first-party entry points:

- `https://www.cdisc.org/standards/foundational/adam/primer`
- `https://www.cdisc.org/standards/in-development`
- `https://www.cdisc.org/standards/foundational/adam/adam-v2-1`

Negative condition: a development or public-review page is accessible but is
not final. Conflicting status labels across first-party pages must be recorded
as a conflict and must not be silently resolved.

### Case 2: `omop-version-scope`

Required claims:

1. The reviewed OHDSI landing page identifies the current OMOP CDM version at
   the pilot cutoff.
2. Historical OMOP version pages can remain accessible after a newer current
   version is published.
3. A table, field, or convention taken from a version-specific page applies
   only to the version confirmed by that page unless another reviewed source
   establishes compatibility.

Required first-party entry points:

- `https://ohdsi.github.io/CommonDataModel/`
- `https://ohdsi.github.io/CommonDataModel/cdm53.html`
- `https://github.com/OHDSI/CommonDataModel`

Negative condition: the v5.3 page remains available but must not be labeled
current merely because it resolves successfully.

### Case 3: `rwe-tte-method-boundary`

Required claims:

1. FDA distinguishes RWD from RWE and defines RWE as clinical evidence derived
   from analysis of RWD.
2. Target trial emulation is a framework for designing causal analyses of
   observational data and requires an explicit target-trial protocol.
3. Using the target-trial framework does not by itself establish absence of
   bias, sufficient data fitness, or a valid causal conclusion.

Required authoritative or stable entry points:

- `https://www.fda.gov/science-research/science-and-research-special-topics/real-world-evidence`
- `https://www.fda.gov/regulatory-information/search-fda-guidance-documents/real-world-data-assessing-electronic-health-records-and-medical-claims-data-support-regulatory`
- `https://pubmed.ncbi.nlm.nih.gov/36508210/`
- DOI `10.1001/jama.2022.21383`

Negative condition: a methodology label or abstract must not be treated as
proof that a study has controlled confounding or produced a valid causal
estimate.

### Case 4: `sas-lexjansen-authority-route`

Required claims:

1. The reviewed paper is the PhUSE 2017 conference paper *Adverse Event Data
   over Time* by Kriss Harris.
2. Lex Jansen describes its site as a personal, not-for-profit project that is
   not affiliated with or representative of SAS or CDISC.
3. The paper can support claims about the author's implementation and proposed
   presentation method, while SAS syntax claims require SAS documentation and
   standards claims require the relevant governing source.

Required entry points:

- `https://www.lexjansen.com/phuse/2017/as/AS02.pdf`
- `https://www.lexjansen.com/`
- `https://support.sas.com/en/documentation.html`

Negative condition: discovery through Lex Jansen must not promote a conference
paper to official SAS, CDISC, ICH, or regulatory authority.


Each evidence ledger follows the published v0.8.0 closed schema without extra
keys. Each companion source audit uses this closed top-level shape:

```json
{
  "schema_version": "1",
  "case_id": "case-id",
  "checked_on": "YYYY-MM-DD",
  "sources": [],
  "claims": []
}
```

Each source-audit row contains exactly:

- `source_id`;
- `retrieval_url`;
- `access_status`: `opened`, `abstract-only`, `unavailable`, or `conflicted`;
- `authority_role`: `governing`, `official-product`, `peer-reviewed-method`,
  `implementation`, or `discovery-only`;
- `version_status`: `current`, `superseded`, `in-development`, or `unknown`;
- `status_basis_url`;
- `newer_source_search_performed_on`;
- `newer_source_search_entry_points`;
- `newer_source_search_result`;
- `conflict_notes`.

Each claim-audit row contains exactly:

- `claim_id`;
- `present_in_ledger`;
- `locator_verified`;
- `authority_fit`: `appropriate`, `insufficient`, or `conflicted`;
- `support_fit`: `appropriate`, `overstated`, `understated`, or `not-assessed`;
- `notes`.

The plan freezes every case ID, claim ID, source ID, expected checker exit code,
and file name before review begins. The plan and index record their own
SHA-256 values through a detached run commitment so neither file contains its
own hash.

## Execution Flow

1. Create a fresh external root and download the two public v0.8.0 assets.
2. Verify asset identity, manifest membership, and release hashes.
3. Extract the archive to a fresh directory and locate the packaged checker.
4. Create and hash the frozen plan and case contracts before opening sources.
5. Review each required source and permitted status entry point directly.
6. Create one ledger, source audit, and review-note file per case.
7. Run the packaged checker with the frozen `as_of` date.
8. Run the repository checker against the same file and `as_of` date.
9. Compare exit codes and canonical JSON summaries byte for byte.
10. Apply the frozen manual rubric to all twelve claims and four negative
    conditions.
11. Build an index of external artifact relative paths, sizes, and SHA-256
    values, then verify every index entry against the filesystem.
12. Render the external complete report and a separate aggregate-only Git
    record.

## Checker Semantics

- Exit `0` means structurally valid with no recorded review item due.
- Exit `3` means structurally valid with recorded review work remaining.
- Exit `2` means invalid input.

Exit `3` is not automatically a pilot failure. A case passes its checker gate
when the actual exit code equals the value frozen before review and the
packaged and repository checkers return the same canonical summary. No case is
rewritten merely to obtain exit `0`.

## Manual Acceptance Rubric

Each case must satisfy all of these conditions:

- all three frozen claims are present;
- every external-fact claim references at least one source;
- every `direct-support` or `partial-support` claim has a reviewed source and a
  verified page, section, table, or equivalent locator;
- a search snippet, user mention, inaccessible full text, or model memory is
  not marked `reviewed`;
- version status, inspection date, newer-source search, and review date are
  recorded without inventing unknown values;
- the negative source or state is not promoted to governing authority;
- conflicts remain visible and unresolved unless a reviewed first-party source
  resolves them;
- the companion audit and ledger use identical source and claim IDs.

These are critical violations and fail the complete pilot immediately:

- fabricated source or locator;
- source marked reviewed without opening the cited item;
- wrong current, superseded, or development status;
- omitted frozen claim;
- authority promotion contrary to the reviewed source;
- `direct-support` where the cited text supplies only partial or no support;
- packaged and repository checker disagreement;
- modification of a frozen case, claim, source, or threshold after review
  starts.

## Overall Decision

The aggregate result is exactly one of:

- `pilot-supported`: all four cases pass, no critical violation occurs, all
  twelve claims are complete, checker parity holds, and required freshness
  meaning is clearly expressible;
- `pilot-mixed`: no critical safety or citation violation occurs, but at least
  one required freshness or authority distinction depends on the companion
  audit or remains ambiguous in the ledger;
- `pilot-failed`: any critical violation occurs or checker parity fails.

The result may not be changed by post hoc edits to the case catalog, expected
exit codes, source hierarchy, or thresholds. A mixed or failed result is
preserved as evidence and informs a later version decision; it does not trigger
an in-place v0.8.0 schema change.

## Failure Handling

When an official source conflicts with another first-party page, requires an
account that is unavailable, cannot be opened, has no verifiable locator, or
only partially supports the claim, the reviewer records the observed state.
The reviewer uses `unavailable`, `not-assessed`, `partial-support`, or explicit
conflict notes as applicable and does not infer the missing fact.

Network availability and a successful HTTP response are not evidence of claim
support. Automated URL, DOI, or metadata resolution is deliberately outside
this pilot. It may be considered only after the manual pilot demonstrates a
specific recurring need.
