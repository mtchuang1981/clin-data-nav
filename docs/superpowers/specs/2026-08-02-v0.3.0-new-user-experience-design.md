# Clinical Data Research Navigator v0.3.0 Design

- **Date:** 2026-08-02
- **Status:** Approved after recommendation audit
- **Target release:** `v0.3.0`

## 1. Decision

Implement the comprehensive repository-local v0.3.0 optimization in one
coherent release. The release will add four explicit output depths, complete
the beginner information architecture, make every Eval catalog case have a
scored baseline/forward pair, and close the remaining repository-local trust
gaps that were identified after v0.2.2.

The implementation must preserve the existing authority routing, public/private
boundary, optional `build-rwe-sap` relationship, RWD/RWE distinction, TTE
readiness gate, data-contract requirements, and execution-maturity gate.
Reducing cognitive load must never make an unsafe answer look executable.

## 2. Alternatives considered

### 2.1 Minimal experience patch

Add the four output depths and a glossary, but leave the current README,
partial Eval fixtures, cross-runner packaging gap, and metadata debt largely
unchanged. This is the smallest change, but it would immediately require
another cleanup release and would leave the new modes weakly evidenced.

### 2.2 Comprehensive repository-local release — selected

Implement the output-depth contract, beginner navigation, complete scored Eval
coverage, README decomposition, cross-runner artifact comparison, current
GitHub Actions runtime, citation and security documentation, and synchronized
v0.3.0 metadata together. This is larger, but each part shares the same user
journey and acceptance matrix, so one coherent release has lower long-term
maintenance cost than multiple partially overlapping patches.

### 2.3 Plugin product expansion

Package and publish a separate ChatGPT or marketplace Plugin in the same
release. This crosses a different product, schema, distribution, permission,
and review boundary. It is excluded from v0.3.0. The README will explain that
this repository distributes an Agent Skill from GitHub and does not claim a
separate public Plugin-directory listing.

## 3. Goals

1. Give beginners a useful first answer without forcing a full implementation
   specification onto every question.
2. Make response depth explicit, predictable, user-overridable, and testable.
3. Provide plain-language definitions for the repository's essential concepts
   and three guided learning paths.
4. Keep the public READMEs focused on installation, first use, output choice,
   boundaries, and navigation; move maintainer detail to dedicated documents.
5. Give every Eval catalog case a deterministic baseline and forward result,
   with coverage for all four output depths.
6. Compare Windows and Ubuntu package artifacts directly in CI and in the
   guarded Release workflow.
7. Remove the current GitHub Actions Node.js 20 deprecation annotations while
   retaining full-SHA action pinning.
8. Synchronize all current version and release surfaces to `0.3.0` without
   changing historical releases.

## 4. Non-goals and external boundaries

- Do not build, publish, or claim a separate Plugin product.
- Do not create or bundle the optional `build-rwe-sap` Skill.
- Do not add private adapters, codingbooks, data dictionaries, physical
  schemas, linkage rules, PII classifications, or production institutional
  code.
- Do not turn deterministic keyword Evals into a claim of clinical validity,
  causal validity, or semantic correctness.
- Do not invent a maintainer's legal name, ORCID, email address, affiliation,
  or brand assets.
- Do not mutate branch protection, repository rulesets, topics, private
  vulnerability reporting, Dependabot settings, tags, or GitHub Releases
  without separate explicit approval immediately before those external
  actions.
- Do not move or overwrite the immutable `v0.2.2` tag or Release.

## 5. Four output depths

Every response must use exactly one primary output depth. A response may link
to a deeper next step, but it must not silently combine all four depths.

### 5.1 Quick explanation

Use for definitions, comparisons, and beginner questions such as “What is
ADaM?” or “How are RWD and RWE different?”

Required output:

- `Output depth: quick explanation`;
- a direct plain-language answer;
- why the concept matters in the user's context;
- one or two common confusions or limits; and
- a short source list using the governing authority.

Do not add an evidence matrix, full data contract, code-maturity checklist, or
implementation mapping unless the user asks to go deeper. Safety caveats still
apply: a short answer may not invent a local schema or make a causal claim.

### 5.2 Evidence navigation

Use when the user needs standards, guidance, source comparison, Lex Jansen or
implementation-literature discovery, or authority conflict resolution.

Required output:

- `Output depth: evidence navigation`;
- decision and search scope;
- authority-ordered search route;
- evidence table with provenance and applicability;
- conflicts, limitations, and unreviewed-source gaps; and
- sources actually reviewed.

Do not copy code from a paper without provenance and reuse review. Search
results and index snippets are leads, not reviewed evidence.

### 5.3 Research design

Use for descriptive, predictive, causal-comparative, measurement, PICO, RWE,
TTE, estimand, phenotype, protocol, or SAP-framing questions that do not yet
request an executable implementation.

Required output:

- `Output depth: research design`;
- primary intent and design route;
- PICO-informed or other design-appropriate question fields;
- time zero, follow-up, outcome, data source, and intended use where relevant;
- RWD fitness and RWE claim boundary;
- TTE readiness only for causal-comparative questions;
- bias, confounding, missing-design, and validation gaps; and
- optional `build-rwe-sap` handoff status when applicable.

This mode may define logical data needs, but it must not imply that a complete
SAP, estimand, causal result, or executable institutional program exists.

### 5.4 Implementation specification

Use when the user requests SAS, SQL, R, Python, metadata, mappings, validation
rules, derivations, or an implementation-ready contract.

Required output:

- `Output depth: implementation specification`;
- decision and governing evidence;
- the full logical data contract, including grain, keys, joins, coverage,
  types, time anchors, code systems, missingness, precedence, lineage, and
  acceptance fixtures;
- exactly one existing code-maturity label;
- implementation or pseudocode only when permitted by the execution gate; and
- every validation gap that blocks the next maturity level.

Without the required Adapter, current metadata, parameters, and fixtures, this
mode must emit `SPECIFICATION ONLY — NOT EXECUTABLE` and must not produce SQL-
or code-shaped placeholders that could be mistaken for physical objects.

## 6. Output-depth selection

The Skill will select depth in this order:

1. Honor an explicit user choice when it does not conflict with a safety gate.
2. Otherwise infer the primary intent from the requested deliverable.
3. Choose the least intensive depth that fully answers the request.
4. Ask one concise clarification only when two depths would produce materially
   different deliverables and the ambiguity cannot be resolved from context.
5. Offer the next deeper mode as an optional follow-up instead of pre-emptively
   generating it.

Examples:

| Request | Default depth |
|---|---|
| “What is SDTM?” | Quick explanation |
| “Find the governing TEAE sources and relevant SAS literature” | Evidence navigation |
| “Frame a comparative RWD study and assess TTE readiness” | Research design |
| “Create a reviewed SAS derivation specification” | Implementation specification |

The depth changes presentation and required sections, not evidence authority or
safety. No depth may bypass provenance, public/private boundaries, or the
execution gate.

## 7. Skill and reference architecture

### 7.1 `SKILL.md`

Update the core principle from one universal output shape to a two-stage rule:

1. choose the output depth; and
2. apply the authority, contract, maturity, and validation requirements needed
   by that depth.

Add a compact selection table and common failure modes for over-answering a
quick question, under-answering an implementation request, and using a depth
label to evade safety requirements.

### 7.2 Output template

Refactor `references/evidence-output-template.md` into:

- a small common header containing output depth, decision, confirmed facts,
  assumptions, limitations, and sources; and
- four mode-specific section contracts matching Section 5.

The existing full Evidence → Contract → Code maturity → Validation gaps shape
remains authoritative for implementation specifications. It is no longer
mandatory for a simple definition.

### 7.3 Beginner reference

Add one installable reference,
`references/output-depths-and-learning-paths.md`, containing:

- the selection decision table;
- the four output contracts;
- the beginner glossary used at response time; and
- the three learning-path routes.

`SKILL.md` reads it for first-use guidance, explicit mode requests, and unclear
deliverable-depth questions. Other references remain one-hop and are loaded
only when relevant.

## 8. Beginner glossary and learning paths

### 8.1 Glossary

Create aligned English and Traditional Chinese human documentation for at
least:

- authority level;
- data contract;
- execution gate;
- code maturity;
- fixture;
- Adapter;
- governing artifact;
- provenance;
- grain;
- key and join cardinality;
- time zero;
- estimand;
- phenotype;
- RWD and RWE; and
- specification-only versus executable output.

Definitions must be short, use synthetic examples, and preserve the governing
technical meaning. Existing CDISC, SDTM, ADaM, PICO, TTE, and
`build-rwe-sap` explanations remain linked rather than duplicated verbatim.

### 8.2 Learning paths

Provide three explicit beginner routes:

1. **Clinical trials and CDISC:** CDISC → SDTM → ADaM → protocol/SAP →
   implementation evidence.
2. **RWD and RWE:** intent → PICO-informed fields → RWD fitness → RWE claim →
   TTE readiness when causal-comparative.
3. **Institutional implementation:** public evidence → logical data contract →
   approved Adapter → live metadata → fixtures → executable/validated status.

Each path states prerequisites, a first safe prompt, expected output depth,
what the path cannot prove, and the next document to read.

## 9. README information architecture

Keep `README.md` and `README.zh-TW.md` aligned in section order and meaning.
Their primary path becomes:

1. one-sentence purpose and non-goal plus a validation badge that points to
   `.github/workflows/validate.yml`;
2. prerequisites and `npx` installation;
3. 60-second first success;
4. choose an output depth;
5. choose a learning path;
6. understand the public/private and executable/non-executable boundaries;
7. product boundary: GitHub-distributed Agent Skill, not a claimed public
   Plugin-directory listing;
8. links to glossary, examples, installation alternatives, and maintainer
   documentation.

In each README, the install command, first safe prompt, and expected-output
summary must all appear within the first 30 non-blank lines. Language links,
badges, code fences, and wrapped prose may add physical lines but may not push
the first-success path behind governance or maintainer material.

Move detailed manual Release installation and source-checkout installation to
aligned `docs/installation.md` and `docs/installation.zh-TW.md`. Keep
contributor setup in `CONTRIBUTING.md`, repository validation in
`CONTRIBUTING.md`, and release operations in `docs/release.md`. The README may
show the four commands only as a linked maintainer summary, not as part of the
beginner success path.

The installation documents must include stage-specific troubleshooting for a
missing Node.js/npm/npx command, failed project-local installation, missing
Skill discovery, stale discovery after update, checksum mismatch, and an
existing destination that the safe installer refuses to overwrite. Recovery
instructions must not recommend disabling verification or deleting an
unresolved destination blindly.

Implementation must verify the current official OpenAI and Agent Skills
terminology before editing the Codex, ChatGPT, Skill, or Plugin wording. If an
official product claim cannot be verified, use a narrower repository-local
statement instead of guessing.

## 10. Complete offline Eval evidence

### 10.1 Catalog contract

Add an `output_depth` field to every Eval case. The evaluator schema accepts
exactly the four normalized depth values and rejects missing or unknown values.

Retain the current 11 cases and add one focused beginner case for a quick ADaM
explanation. Map the catalog so all four depths have at least one case.

### 10.2 Fixture coverage

Every catalog case must have:

- one response-only synthetic baseline fixture that demonstrates a meaningful
  pre-v0.3 gap and scores below the fixed pass threshold; and
- one response-only synthetic forward fixture that satisfies the deterministic
  contract, contains no forbidden pattern, and reaches the fixed threshold.

No fixture may contain private institutional facts, copied external prose, or
real patient data. Forward fixtures are contract examples, not clinically
validated answers.

### 10.3 Reporting

Update `evals/README.md` to list all catalog cases, their output depth, baseline
score, forward score, and pass/fail state. A filesystem-derived contract test
must require complete one-to-one catalog, baseline, forward, and table-row
coverage and must recompute every displayed score.

The report must continue to state that deterministic rules-based scores prove
only regression-contract compliance. They do not prove semantic correctness,
source accuracy, clinical validity, causal validity, or complete real-world
coverage.

## 11. Cross-runner package identity

### 11.1 Validation workflow

After each Ubuntu and Windows matrix job passes the existing four commands, it
will build the public ZIP and manifest into an OS-specific artifact and upload
only those public files with short retention. A dependent read-only comparison
job downloads both artifacts and requires byte-identical ZIP and manifest
files.

Artifact names must include the verified commit and operating system. The
comparison job must fail on missing, extra, renamed, or mismatched files.

### 11.2 Release workflow

The guarded Release validation matrix will likewise build and upload the two
OS candidates. The read-only build job will download and compare them before
assembling the immutable Release bundle. It may publish only one of two already
identical candidates. The final writer boundary remains unchanged: no checkout,
Python, dependency installation, or repository-code execution.

### 11.3 Actions runtime

Replace actions that still declare Node.js 20 with current official majors
that declare the supported GitHub-hosted runner runtime. Verify upstream
release notes, pin every action to a full commit SHA, retain the human-readable
version comment, and keep permissions read-only except for the final writer.

## 12. Repository metadata and security documentation

### 12.1 Citation

Enhance `CITATION.cff` with the repository URL, source-code URL, and a
non-invented contributor identity. Add `date-released` only when the actual
v0.3.0 publication date is fixed during an approved publication step. A legal
name, affiliation, email, ORCID, DOI, or Zenodo record may be added only from
explicit maintainer input or a verified public record; absence must not be
filled by inference.

Record a short Zenodo decision in the repository-setting checklist: whether a
DOI is useful for the project's citation goals, what account/integration would
be required, and why no DOI may be claimed before a verified deposition
exists.

### 12.2 Skill UI metadata

Revise the default prompt to be beginner-readable and to mention output-depth
selection while remaining within the validator's single-sentence and 200-code-
point limits. Add icon or color metadata only if the current official schema
supports those keys and the corresponding public asset has been explicitly
approved. Unsupported decorative keys must not be invented.

### 12.3 Security

Expand `SECURITY.md` with supported versions, what must never be reported in a
public issue, the currently available private reporting route, expected
acknowledgement boundaries without an invented service-level promise, and the
existing accidental-private-data incident response.

Add `docs/repository-settings.md` as the operator checklist for:

- required Ubuntu and Windows status checks;
- recommended topics: `clinical-research`, `rwe`, `cdisc`, `omop`, `sas`, and
  `agent-skills`;
- private vulnerability reporting;
- Dependabot security updates; and
- optional Zenodo DOI evaluation; and
- verification after each setting change.

The document is not evidence that an external setting is enabled. Actual
settings must be re-read after a separately approved mutation.

## 15. Test strategy

All behavior and workflow changes follow RED → GREEN → REFACTOR:

1. Add failing mode-selection and mode-output contract tests.
2. Add failing README, glossary, learning-path, and product-boundary tests.
3. Add failing Eval schema, complete-fixture, score-table, and depth-coverage
   tests.
4. Add failing cross-runner workflow and Node-runtime contract tests.
5. Add failing version, citation, UI metadata, security, and repository-setting
   documentation tests where behavior is machine-verifiable.
6. Apply the smallest implementation change for each focused red state.
7. Run focused tests after every task and the complete verification set at the
   end.

Human prose will be reviewed for accuracy and alignment rather than protected
by brittle exact-text assertions. Tests will exercise the behavior or derived
contract that the prose enables.

## 16. Failure prevention

- **Quick mode becomes unsafe:** safety and authority rules are global and
  cannot be disabled by selecting a shorter response.
- **Every answer remains huge:** the least-sufficient-depth rule and Eval cases
  reject full-contract overproduction for beginner definitions.
- **Implementation requests become shallow:** implementation-specification
  tests require the full contract and maturity gate.
- **Depth labels become decorative:** every depth has distinct required and
  prohibited output characteristics in tests and Evals.
- **Keyword scores are mistaken for validity:** every Eval report repeats the
  deterministic-regression limitation and retains human review.
- **README moves break installation:** contract tests execute or structurally
  validate every retained command in its new document.
- **Cross-runner artifacts leak content:** jobs upload only the public ZIP and
  manifest after the boundary scan, with short retention and exact-file checks.
- **Action upgrades weaken trust:** upstream versions are verified, full SHAs
  remain pinned, and permissions are asserted in tests.
- **Branch protection locks out maintenance:** external rules are applied only
  after the exact check names are green and an administrator recovery path is
  confirmed.
- **Citation or branding invents identity:** unknown personal and brand fields
  remain absent until explicitly supplied.

## 17. Acceptance criteria

v0.3.0 is locally ready only when:

- all four output depths have an explicit selection contract and behavior
  tests;
- a quick definition does not require a full data contract, while an
  implementation specification cannot omit it;
- the three learning paths and aligned bilingual glossary exist;
- both READMEs present installation, first success, depth, paths, boundaries,
  and navigation before maintainer detail;
- the install command, first prompt, and expected-output summary occur within
  the first 30 non-blank lines of each README;
- the validation badge targets the real validation workflow;
- detailed installation and contributor procedures remain discoverable and
  verified after moving out of the README, including safe troubleshooting for
  each documented installation failure stage;
- the README does not claim a public Plugin listing;
- every Eval catalog case has an output depth, baseline fixture, forward
  fixture, recomputed score row, and no forbidden response;
- every forward fixture reaches the fixed threshold and every baseline fixture
  remains below it;
- Windows and Ubuntu package ZIPs and manifests are compared byte-for-byte in
  both validation and Release workflows;
- workflow files use officially verified Node.js 24-capable action majors and
  remain pinned to full commit SHAs;
- citation, UI prompt, security documentation, repository-setting checklist,
  version metadata, changelogs, and v0.3.0 Release notes are synchronized;
- a fresh Python 3.11 environment can still install `.[dev]` and execute the
  complete verification set;
- `.baoyu-skills/baoyu-translate/EXTEND.md` and other unrelated local-tool
  configuration remain absent from the tracked tree;
- the test count exceeds the current 222 without deleting, skipping, xfail-ing,
  or weakening an existing test;
- `python -m pytest -q`, `python scripts/validate_skill.py`,
  `python scripts/check_public_boundary.py`, and
  `python scripts/package_skill.py --check-reproducible` all exit zero;
- `git diff --check` exits zero and the complete diff contains no private or
  unrelated material; and
- no external GitHub setting, tag, or Release is changed without its separate
  approval and post-change verification.

## 18. Publication boundary

After local implementation and evidence review, the project will stop before
external mutation. A later approved publication sequence must:

1. push the exact reviewed commit;
2. require the exact commit's updated CI, including cross-runner comparison,
   to succeed without the Node.js 20 deprecation annotation;
3. optionally apply and verify separately approved repository settings;
4. create a new annotated `v0.3.0` tag without moving an older tag;
5. dispatch the guarded Release workflow;
6. independently download and verify the ZIP and manifest; and
7. record the public evidence in a new dated verification report.
