# Clinical Data Research Navigator v0.4.0 Release Design

Date: 2026-08-09
Target tag: `v0.4.0`
Publication: annotated tag plus guarded GitHub Release

## 1. Goal

Publish the reviewed effectiveness-evaluation framework as v0.4.0 without
claiming that a human pilot was conducted or that the Skill is proven
effective. The public Release must contain exactly the reproducible Skill ZIP
and its manifest, produced only after Ubuntu and Windows candidates are
byte-identical.

## 2. Selected approach

Use the repository's existing guarded Release workflow. A release-preparation
commit synchronizes every current-version surface to `0.4.0`, fixes the
publication date, adds bilingual changelog content and static bilingual Release
notes, and updates the workflow's version/notes assertions. After local and
remote validation are green, create a new annotated `v0.4.0` tag at that exact
commit, push only the new tag, and manually dispatch the guarded workflow.

Manual local asset upload is rejected because it would bypass cross-runner
comparison and the final writer's remote tag/release rechecks. A tag-only
publication is rejected because it would omit the verified installer assets.

## 3. Release-preparation surfaces

Synchronize only active release metadata; preserve historical releases:

- `pyproject.toml`
- `scripts/package_skill.py`
- `scripts/install_local.py`
- `CITATION.cff`
- `CHANGELOG.md`
- `CHANGELOG.zh-TW.md`
- `README.md`
- `README.zh-TW.md`
- `docs/installation.md`
- `docs/installation.zh-TW.md`
- new `docs/releases/0.4.0.md`
- `.github/workflows/release.yml`
- version/release contract tests

The v0.4.0 notes describe the framework, contracts, safeguards, bilingual
reporting, documentation, Python 3.11 verification, and deterministic release
controls. They explicitly state that repository and synthetic evaluations do
not constitute human recruitment, real participant data, pilot findings,
clinical validation, or proof of effectiveness.

## 4. Local release gates

Before the release commit and again after it:

1. run the complete pytest suite;
2. run Skill validation;
3. run the public-boundary scan;
4. run the reproducible package check;
5. run both deterministic renderer checks;
6. build the ZIP and manifest;
7. run `verify_release.py artifacts`;
8. inspect the ZIP file list and manifest schema;
9. calculate ZIP and manifest SHA-256 values; and
10. require a clean `main` worktree.

Run the full suite and the four required gates with the host runtime and the
approved official Python 3.11.9 temporary runtime. The release commit must be
pushed before tagging, and its required main checks must be successful.

## 5. Tag and guarded publication

- Refuse an existing local or remote `v0.4.0` tag or Release.
- Create `v0.4.0` as an annotated tag whose message uses the reviewed static
  Release notes.
- Record the tag object and peeled commit, then push the new tag without moving
  any existing tag.
- Dispatch `.github/workflows/release.yml` with `tag=v0.4.0`.
- Require preflight, Ubuntu validation, Windows validation, byte comparison,
  immutable bundle creation, transit checksum verification, and final publish
  to succeed.
- The final writer must recheck that the remote annotated tag object and peeled
  commit equal the preflight values and that no Release already exists.

## 6. Public verification and evidence

After publication, download both public assets into a fresh temporary
directory. Verify their filenames, sizes, manifest structure, ZIP contents,
archive SHA-256, and manifest SHA-256 independently. Confirm the public Release
has exactly those two assets and points to the intended tag.

Create a dated post-release verification report recording the main commit,
annotated tag object, peeled commit, main validation URL, guarded Release
workflow URL, public Release URL, asset IDs/sizes/digests, and independently
verified ZIP/manifest relationship. Commit and push this report after the
Release without moving the tag or editing/replacing the published Release.

## 7. Failure boundaries

- Any local or remote test, gate, package, checksum, tag, workflow, or asset
  mismatch stops publication.
- Never force-move or recreate `v0.4.0`.
- Never overwrite an existing v0.4.0 Release; use a later patch version for a
  correction.
- Do not include human data, condition keys, private adapters, private task
  packs, or free-text participant material in the repository or assets.
- Do not turn the synthetic effectiveness example into a real-use claim.

## 8. Acceptance criteria

The release is complete only when the release-preparation commit is on main,
all required checks are successful, `v0.4.0` is an annotated remote tag, the
guarded workflow succeeds, the public Release contains exactly the verified ZIP
and manifest, independent download verification succeeds, and the dated
post-release evidence commit is pushed.
