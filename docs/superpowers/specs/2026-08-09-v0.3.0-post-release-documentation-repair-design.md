# v0.3.0 Post-Release Documentation Repair Design

- **Date:** 2026-08-09
- **Status:** Approved scope awaiting written-spec review
- **Target:** `main` after the immutable `v0.3.0` publication

## 1. Decision

Repair the repository's post-release documentation contract without changing
the published `v0.3.0` tag, GitHub Release, packaged Skill, or version number.
The change will make current installation and security guidance truthful,
record the already verified public publication evidence, and prevent the same
candidate-versus-published drift in future releases.

## 2. Problems to correct

1. The English and Traditional Chinese installation guides still describe
   `v0.3.0` as a future, unpublished target even though the Release exists.
2. `SECURITY.md` still names `0.2.x` as the newest supported release line.
3. The approved publication sequence requires a new dated public verification
   report, but the repository contains only the earlier local-candidate report.
4. `docs/release.md` verifies public assets but does not require the evidence
   to be saved, committed, and pushed after publication.
5. Existing tests enforce the stale candidate and security wording instead of
   rejecting it.

## 3. Scope

### 3.1 Tests first

Update repository metadata tests before production documentation so they fail
for the observed drift and require:

- both installation guides to identify `v0.3.0` as published and retain the
  verified ZIP/manifest workflow;
- `SECURITY.md` to identify `0.3.x` as the supported line and not mark `0.2.x`
  as supported;
- `docs/release.md` to require a new dated post-release evidence report; and
- the new report to contain the exact reviewed main commit, annotated tag
  object and peeled commit, validation and Release workflow URLs, Release URL,
  asset IDs, sizes, and SHA-256 values.

Each changed contract must be observed failing for the intended reason before
the corresponding documentation is changed.

### 3.2 Documentation changes

Modify only:

- `docs/installation.md`;
- `docs/installation.zh-TW.md`;
- `SECURITY.md`;
- `docs/release.md`;
- `tests/test_project_metadata.py`; and
- a new `docs/verification/2026-08-09-v0.3.0-publication.md`.

The publication report will distinguish verified public facts from external
settings that remain disabled or unevaluated. It will record the final public
asset hashes rather than the earlier candidate hashes.

## 4. Historical and external boundaries

- Do not edit `docs/verification/2026-08-02-v0.3.0-local.md`; it is immutable
  historical evidence for an earlier candidate.
- Do not move, replace, or edit the `v0.3.0` tag or GitHub Release.
- Do not change package contents, package version, changelogs, or
  `CITATION.cff`.
- Do not enable branch protection, rulesets, topics, private vulnerability
  reporting, Dependabot, or Zenodo integration in this repair.
- Do not invent author identity, ORCID, DOI, icon, color, or service-level
  commitments.
- Do not mark all implementation-plan checkboxes retrospectively. The new
  evidence report will provide an as-built disposition without claiming
  unrecorded step-by-step execution evidence.

## 6. Verification and completion

Run focused metadata tests, then the complete required verification:

```text
python -m pytest -q
python scripts/validate_skill.py
python scripts/check_public_boundary.py
python scripts/package_skill.py --check-reproducible
python scripts/render_eval_summary.py --check
git diff --check
```

Review the complete diff and commit the repair on `main`. Pushing remains a
separate external action and is not authorized by this design approval.
